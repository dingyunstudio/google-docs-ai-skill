# Google Docs AI Editing Skill

[繁體中文](README.md) | [English](README.en.md)

[![請我喝杯咖啡](https://ko-fi.com/img/githubbutton_sm.svg)](https://ko-fi.com/dingyunstudio)

**這是一套輔助 AI 操作 Google Docs 的 Skill**，由定沄整合設計工作室依實際應用的方法整理，供 AI 讀取並依循。

這套 Google Docs editing workflow 可在具備相應工具的 ChatGPT Chat 環境中使用。

協助 AI 安全修改 Google Docs：先確認目前文件，再逐單元寫入、立即回讀、驗證文字與結構，最後留下可查證的結果。  
透過這套流程，協助減少 AI 直接操作 Google Docs 時發生逾時或錯誤寫入的風險。

**Skill 提供操作方法與檢查準則，本身不直接連接或修改文件，也不是自動排版、格式優化工具或文件精靈。** 實際讀寫由 AI 使用連接工具執行；使用者確認需求與修改範圍，AI 依核准內容操作，並回讀、驗證及報告結果。

本 Skill 不保證 AI 永不出錯或每次都能完成指定結果；實際成果以當次操作與驗證為準。

## 可以怎麼幫你修改 Google Docs？

以下是 AI 可依本 Skill 協助處理的需求範例，不是 Skill 本身內建的自動化功能。在 Chat 裡直接說你想改什麼，AI 會先讀文件、和你確認做法，再修改並檢查結果。

### 常見修改需求

| 你想做什麼 | 你可以怎麼說 | AI 會怎麼處理 |
|---|---|---|
| **只改指定句子或段落** | 「把第二段最後一句改成我們剛剛定案的版本，其他不要動。」 | 只改指定位置，改完確認文字、標點及前後內容。 |
| **只改重複文字的其中一處** | 「這句出現兩次，只改後面那句，前面不要動。」 | 找到後面那一處修改，保留前面的句子與其他內容。 |
| **接著修改剛更新的文件** | 「我剛剛有更新，你重新看一下，再接著改。」 | 先讀最新內容，再確認修改位置，避免照著舊稿改錯地方。 |
| **整篇統一換字** | 「把這份文件的『草稿』全部換成『定稿』，其他不要動。」 | 找出所有出現位置，換好後檢查有沒有漏改或誤改，保留格式與連結網址。 |
| **整篇整理內容或排版** | 「這篇全部重新排版，文字不要改，原本連結也要留著。」 | 先整理排版草稿，你確認後更新原文件；保留原文字、連結與表格，並檢查版面。 |
| **建立新文件作為正式版本** | 「把這份企劃書整理好，做成新文件，之後我們就用新版。」 | 準備內容與排版，確認後建立新文件，交代正式版本及新的文件連結。 |
| **用整份新稿替換原文件** | 「這份新稿定案了，幫我換掉原本內容，但原連結要保留。」 | 先確認能保留原連結的替換方式與範圍，你確認後處理，再檢查全文、格式與連結。 |

動手前先備份，改完再檢查。以上操作方式沿用定沄整合設計工作室實際應用的方法。

### 適用工作

| 你可以怎麼說 | AI 會怎麼處理 | 最後拿到什麼 |
|---|---|---|
| 「幫我把這份企劃書整理好，做成一份新的 Google 文件。」 | 先準備整份內容與排版，你確認後建立新文件，再檢查線上結果。 | 新的 Google 文件連結，以及整理好的內容與版面。 |
| 「把後面那句『本週內容待確認』改成『本週內容已確認』，其他不要動。」 | 找到你指定的那一句，只改這處；改完立即檢查，確認前後內容保留。 | 原文件中的指定句已修改，其他內容維持原樣。 |
| 「這篇全部幫我重新排版，文字不要改，原本的連結也要留著。」 | 先整理排版草稿，你確認後分段更新原文件；每改一處就檢查，最後核對全文、連結與表格。 | 同一個文件連結，搭配重新整理的版面。 |
| 「剛剛改完，下一段不見了，幫我查一下怎麼救回來。」 | 找出受影響的內容，對照原稿或備份提出復原方案，等你確認後再處理。 | 哪些內容受影響、可以怎麼復原，以及確認後的實際處理結果。 |

文件要保留原連結、另建新檔，或更換正式版本，都依你確認的方案處理；分享設定也一樣。

## 使用方式

### 產品需求（ChatGPT Chat）

- **ChatGPT Plus**：本專案的 ChatGPT Chat 使用基準；實際可用功能仍依帳號與連接工具而定。
- **Google Drive／Docs 連接工具與文件編輯權限**：實際讀取、修改及回讀文件所需。
- **GitHub 連接工具與 repository 讀取權限**：從 GitHub 載入本 Skill 時需要；私人 repository 須另外確認連接帳號有權限。

### 第一次載入

使用者可以從 GitHub 讀取本套件，或在支援本機 Skill 的環境提供本資料夾，請 AI 先讀 [SKILL.md](SKILL.md)。

```text
@GitHub 請讀 dingyunstudio/google-docs-ai-skill
用這個幫我改這篇 doc：[連結]
你先讀裡面的內容，我想把文章的視覺排版整理得更好看、更好讀。
```

### 同一對話繼續使用 DYS

同一對話完成首次載入後，可以用「DYS」指稱這套 Skill，例如：

```text
用 DYS 處理這份文件：[連結]
內文不要改，只整理排版。
```

後續可以直接補充「這句只改後面那一處」或「把草稿全部換成定稿」，AI 會承接已確認的文件與限制。若換了文件、分頁或修改範圍，仍會重新確認目標；新對話也需讓 AI 取得這套 Skill，不能只依賴上一段對話已載入的狀態。

### AI 會怎麼處理你的需求

1. **使用者提供文件連結與想做的事**；已說過的限制直接承接。
2. **AI 依 Skill 讀取適用章節與目前文件**，查明文件身分、分頁、結構與修改邊界，整理[任務契約](templates/task-contract.md)。這是 AI 的工作紀錄，不要求使用者填表或提供 tab ID、revision、index、L／V 等技術資料。能由工具查明的資料由 AI 取得；真正影響目標、範圍或取捨的歧義才請使用者確認。
3. **AI 先提出具體、白話的修改與驗證計畫**，承接使用者對該方案的明確核准，再依原 SOP 規則操作。若只要求視覺排版，先以保留原文字、調整呈現的方向提出方案；不要自行擴成內容改寫。
4. **每個 Write Unit 後立即回讀、驗證**，最後依[證據報告](templates/verification-report.md)交代實際改動、保護範圍、證據與未驗證項目。口語入口不省略原 SOP 的必要報告、核准與停止條件。

### 使用環境與本機安裝

實際修改仍需要環境具備相應 Google Docs 原生工具；讀得到 GitHub，不代表能寫入 Docs 或具備本機文件製作與視覺檢查能力。

只有純文字讀取能力時，可以研究內容或提出建議；需要段落、Heading、樣式、List、Table 或 Link 驗證時，必須取得相應結構資料。缺少寫入或視覺檢查能力時，明確說明目前能交付的範圍，不宣稱已修改或已通過版面驗收。

本機 Skill 的安裝方式依各 AI 工具支援而定；整個資料夾需保留 references、templates、LICENSE 與 LICENSES，讓相對路徑及授權可用。
